## Decisions
Taken by the agent under the author's delegation.
- D1. One pod session runs G-L, then G-R, then G-A1, because G-R and G-A1 need G-L's index; setup is paid once. Reason: the forecast's setup allowances assume separate sessions.
- D2. PyLate's PLAID index instead of the `colbert-ai` library. Reason: the model card names both as compatible; PyLate installs from wheels on the pod, `colbert-ai` compiles CUDA extensions at run time.
- D3. Greedy decoding for G-A1, where `infer.py` samples at temperature 0.7. Reason: a ghost must be repeatable; the fidelity check (C4) runs both in greedy.
- D4. Pod code lives in `src/edge_rag/pod/` and runs under `uv run` from the frozen commit; heavy dependencies (pylate, vllm) go in an optional dependency group `pod`, so the laptop lock stays unchanged for the default group.
- D5. G-L runs in its own locked environment `src/edge_rag/pod/colbert_env` (PyLate 1.6.0 needs transformers <=5.3.0 and fast-plaid builds for torch 2.11, against the harness pins torch 2.13.0 and transformers 5.16.1); G-A1 reaches G-L's index through a local `colbert --serve` endpoint with Search-R1's `/retrieve` API. Dependencies added under the delegation.
- D6. numpy is pinned 2.3.5 on linux x86_64 only (vllm 0.30.0 needs <2.5, as in the old lock); the laptop keeps 2.5.2 and every figure is scored on the laptop.
- D7. A corpus larger than one index chunk (HotpotQA, chunks of 500,000 units) builds its PLAID centroids from a first chunk that is every `stride`-th unit of the whole corpus, then adds the rest through fast-plaid's update; the manifest records the stride. Reason: centroids from the first 500,000 units in file order would not span the corpus. This is not PyLate's single-call build and can move C2; it is stated with the result.
- D8. `colbert_env` takes `torch==2.11.0+cu126` from the PyTorch cu126 index (as the harness does), not PyPI's CUDA 13 build. Reason: F2; the pod driver is CUDA 12.8. The `fast-plaid==1.4.6.2110` linux wheel links only `libtorch`, `libtorch_cpu`, `libtorch_python` and `libc10` (read from the wheel, 2026-10-02), so it is indifferent to torch's CUDA build; the relock changed only the `nvidia-*`/CUDA packages (cu13 to cu12), PyLate and transformers are unchanged.
- D9. After D7's first chunk (500,000 units, which sets the centroids), G-L adds the remaining units 100,000 at a time (`--update-units`). Reason: session 2, commit cc47510, `fast_plaid.update` on a 500,000-unit HotpotQA chunk ran out of the 4090's 24 GB (`torch.OutOfMemoryError` in `update_centroids`, 19.9 GiB held by the chunk's embeddings). Fixed in 3714f09; centroids, PLAID settings and model are unchanged. MultiHop-RAG and MuSiQue (one chunk each) ran at cc47510 and are not affected.
- D10. Session 2 run fixes, none touching a ghost setting: `pod_run.sh` takes the G-L/G-R sets from `GL_SETS` (41506b9); Search-R1's `hf` engine (the `infer.py` reference) moves the model with `.to("cuda")` instead of `device_map="auto"`, which needs `accelerate` (f668934); the retrieval server's python process is ended by pattern, `kill` reached only its `uv run` wrapper (5d13b3f); the retrieval server runs on the CPU because vLLM asks for 0.8 of the GPU and the server held about 7.5 GB (fecc3c2); `HF_HOME=/workspace/hf` on the pod, the float32 Search-R1 checkpoint (about 30 GB) filled the 40 GB container disk.
- D11. C4 and G-A1 move to a second pod session on a host with a CUDA 13 driver (`allowedCudaVersions`), not to a vLLM rebuild. Reason: F4; it changes no code or lock. It is a second setup cost (about 0.3 h) against the "one session" of D1, within the money rule.
- D12. On the author's choice for F3 (2026-10-03), G-L on HotpotQA runs fast-plaid's `update_centroids` through its own CPU branch (`--cpu-centroid-update`, set only for `hotpotqa-dev` in `pod_run.sh`); the rest of the update, the index and the search stay on the GPU, and no ghost setting changes. That branch finds a chunk's outliers with a `usearch` HNSW index (approximate nearest centroid) where the GPU branch uses an exact matmul, so the centroids it adds may differ slightly from what the GPU branch would add; the manifest records the flag. Session 3 runs in two passes on one pod: `GL_SETS="multihop-rag musique" GR_SETS=""` (G-L rebuilt and checked against session 2's rankings by sha256, C4 with the CPU server, G-A1), then `GL_SETS=hotpotqa-dev GR_SETS=hotpotqa-dev`; `GR_SETS` defaults to `GL_SETS`.
- D13. Session 3 run fix, no ghost setting: `pod_run.sh` exports `VLLM_USE_FLASHINFER_SAMPLER=0`. On the CUDA 13 host the C4 vLLM run failed at engine start: FlashInfer 0.6.18 JIT-builds its sampling kernel with the image's `nvcc` 12.4, which rejects `--compress-mode=size` (`pod_run_A.out`, 2026-10-02T23:47:54Z). Search-R1 decodes greedily, and vLLM's sampler takes the argmax when every request is greedy, so the switch only avoids the build.
- D14. Session 3 run fix, no ghost setting: the G-L retrieval server searches a request's queries 32 at a time (`SERVE_BATCH`). G-A1 on MultiHop-RAG sends a turn's 2,255 searches in one request; PLAID on the CPU took the container to its 62 GB limit and the kernel killed the server (cgroup `memory.max_usage_in_bytes` 61,999,996,928 = limit, `oom_kill` 1; `RemoteDisconnected` in `pod_run_C.out`, 2026-10-03T01:24Z). Each query is encoded padded to `query_length` and scored on its own, so the hits do not depend on the batch.

## Findings
- F1. Gold share at 5 (per-question fraction of gold in the top 5, HippoRAG's convention) equals Recall@5 by definition here; it is kept as the bridge label to the literature and adds no separate number.
- F2. `colbert_env` resolves `torch==2.11.0` from PyPI, a CUDA 13 build (it pulls `nvidia-*` cu13 wheels); the pod's driver 570.195.03 (CUDA 12.8) refuses it: `RuntimeError: The NVIDIA driver on your system is too old (found version 12080)`. Next step before G-L can run: route `colbert_env`'s torch to a CUDA 12.x PyTorch index (as the harness does with `pytorch-cu126`) and check that the `fast-plaid==1.4.6.2110` wheel loads against it, or request a pod with a CUDA 13 driver; then rerun the `sync` stage. Not attempted in session 1. Fixed on the laptop by D8; checked on the pod in session 2.
- F3. G-L on HotpotQA (5.23 M units) runs out of the 4090's 24 GB inside `fast_plaid.update`: at cc47510 holding a 500,000-unit chunk (19.9 GiB), and at 3714f09 (D9) in `update_centroids`, whose distance matrix grows with the centroids it adds (3.81 GiB request, 14.3 GiB allocated). Two failed attempts: the stage stops under the recipe, G-R on HotpotQA does not run, and C2 is not measured. Options for the author: a larger-memory GPU for this one index (a hardware change, no ghost setting), or the CPU path of `update_centroids` (fast-plaid's own branch); either is a new attempt that needs the author's word. Session 3 (D12, the author's choice): third failure, CUDA OOM in `fast_plaid_rust.update` at 2,675,758 units; the stage is closed as failed, G-R on HotpotQA not run, C2 not measured.
- F4. vLLM 0.30.0 (CUDA 13 build) fails on the pod's driver 570.195.03 (CUDA 12.8): `cudaHostGetDevicePointer failed: CUDA driver version is insufficient for CUDA runtime version`. The `nvidia/cu13/lib` path of the remote-gpu skill only helps where the driver is CUDA 13; candidate skill note at phase close. The hf reference half of C4 ran (traces kept in `data/phase02/searchr1/musique/compare-hf-50`, made with the GPU server, to be rerun with the CPU server next session for a like-for-like C4).
- F5. G-L is not reproducible across index builds. Rebuilt at 9ea70da on the session 3 host, the rankings differ from session 2's in every row (sha256 of the uncompressed rows differs too): depth-100 overlap 0.960 (multihop-rag) and 0.932 (musique), identical top-10 in 185/2,255 and 107/2,417 questions (measured, laptop comparison). FS@2,048 of the rebuilt rankings: 187 (multihop-rag, equal) and 540 (musique, against 533) (measured, `edge-rag score`). Session 2's G-L and G-R files stay the reported ones; session 3's are kept in `data/phase02/session3/rankings/`. Whether the cause is run-to-run (PLAID k-means on the GPU) or the host change is not settled: the same-host rebuild did not run (its driver script died at a full volume; F6). Candidate C-level note: G-L figures carry a build-to-build spread of this size.
- F6. G-A1 did not complete. First attempt (d65a7ca): the CPU retrieval server was killed by the container's 62 GB memory limit on a 2,255-query request (D14). Second attempt (faf20db): after 2.0 h the CPU server was still answering MultiHop-RAG's searches (about 16 cores busy, GPU idle, no progress log); stopped at 04:07Z for the session's token budget, so no G-A1 ranking exists. Also: the 100 GB volume filled (HotpotQA index 18 GB, two venvs 23 GB, HF cache 31 GB), which killed the chained same-host rebuild and left the pod idle about 40 minutes (02:06Z found idle). Next step for the author: G-A1 needs a faster retrieval path, either the server on the GPU beside vLLM (lower `gpu_memory_utilization`, a run setting) or a per-turn progress log and a measured rate before committing the hours.
